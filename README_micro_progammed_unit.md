# Microprogrammed Control Unit — Revision Notes

Complete revision notes on the Microprogrammed Control Unit (Morris Mano) — covering structure, instruction execution flow, fetch cycle, datapath, and its link to RISC vs CISC pipelining.

---

## 1. Why Microprogrammed Control Exists

| Type | How it works |
|---|---|
| **Hardwired Control** | Control signals generated by fixed logic circuits (combinational logic + flip-flops) |
| **Microprogrammed Control** | Control signals generated by a **stored program (microprogram)** sitting in a special memory called **Control Memory (CM)** |

**Key idea**: Instead of hardwiring logic gates to generate control signals, control signals are stored as **binary words (microinstructions)** in memory. The control unit becomes a tiny computer inside the computer — its "program" is the microprogram, its "instructions" are microinstructions.

> CISC processors rely heavily on this — complex instructions are broken down into sequences of stored micro-operations.

## 2. Core Building Blocks

```
                ┌─────────────────────┐
                │   Control Memory     │  (ROM)
                │  (stores microcode)  │
                └──────────┬───────────┘
                           │
              ┌────────────┴────────────┐
              │  Control Address Register │ (CAR) — holds address of next microinstruction
              └────────────┬────────────┘
                           │
              ┌────────────┴────────────┐
              │   Control Word (CW)      │ — output of CM, read at that address
              └────────────┬────────────┘
                           │
          ┌────────────────┴─────────────────┐
          │        Microinstruction            │
          │  (Control field + Sequencing field)│
          └────────────────┬─────────────────┘
                           │
              ┌────────────┴────────────┐
              │  Next Address Generator   │ (Microprogram Sequencer)
              └────────────┬────────────┘
                           │
              feeds back into CAR (decides next microinstruction address)
```

### Key Terms

| Term | Meaning |
|---|---|
| **Control Word (CW)** | A word whose bits specify one or more micro-operations for the system |
| **Microinstruction** | Each control word in control memory — defines a set of micro-operations |
| **Microprogram** | Sequence of microinstructions that together implement one machine instruction |
| **Control Memory (CM)** | ROM/RAM storing all microinstructions |
| **Control Address Register (CAR)** | Holds address of the next microinstruction to be read from CM |
| **Control Data Register / Pipeline Register** | Holds the microinstruction currently being executed (fetched from CM) |
| **Microprogram Sequencer** | Logic that determines the **next address** to load into CAR |
| **Dynamic microprogramming** | CM is writable (RAM) — allows microprogram modification |
| **Static microprogramming** | CM is ROM — cannot be altered |

## 3. How an Instruction Actually Executes — Step by Step

### Step 1: Machine instruction is fetched
The CPU fetches a machine-level instruction (e.g., `ADD`, `MOV`) from main memory into the **Instruction Register (IR)**.

### Step 2: Opcode goes to a Mapper
The **opcode** portion is sent to a **mapping logic circuit**, converting it into the **starting address in Control Memory** where that instruction's microprogram begins.

> `ADD` → mapper → "microprogram for ADD starts at CM address 0x40"

### Step 3: Starting address loads into CAR
This starting address is loaded into the **Control Address Register (CAR)**.

### Step 4: First microinstruction is fetched from CM
The CAR value addresses Control Memory, and the microinstruction stored there is read into the **control register (pipeline register)**.

### Step 5: Microinstruction is executed
The **control field** is decoded, generating actual control signals driving ALU operations, register transfers, memory read/write, bus selection.

### Step 6: Next Address is determined
The **sequencing field / address field** tells the **Microprogram Sequencer** what to do next:
- Next sequential address (CAR + 1)
- Jump/branch to a specific address (conditional or unconditional)
- Return to the fetch routine (if this was the last microinstruction)

### Step 7: Repeat until instruction completes
Steps 4–6 repeat until the entire microprogram for that machine instruction finishes.

### Step 8: Return to Fetch Cycle
Control returns to the **fetch routine microprogram**, fetching the *next* machine instruction — process repeats.

## 4. Microinstruction Format — Horizontal vs Vertical

| Aspect | Horizontal | Vertical |
|---|---|---|
| Word length | Longer | Shorter |
| Speed | Faster (no decoding delay) | Slower (needs decoding) |
| Parallelism | High (many control lines at once) | Low (usually one operation per field) |
| Hardware | Simple decoding logic | Needs decoder circuit |
| Bit meaning | Each bit = one control signal | Control signals encoded, need decoder |

## 5. Fields Within a Microinstruction

```
┌─────────────────┬──────────────────┬────────────────────┐
│   Control Field   │   Condition Field  │   Branch/Address     │
│ (micro-operations)│  (selects status  │      Field           │
│                   │   bit to test)     │  (next address info) │
└─────────────────┴──────────────────┴────────────────────┘
```

| Field | Purpose |
|---|---|
| **Control field** | Specifies the micro-operation(s) to be performed |
| **Condition field** | Selects a status/flag bit (Carry, Zero) to test for conditional branching |
| **Branch field** | Specifies the address to branch to, and type of branching (unconditional, conditional, mapping) |

---

## 6. Address Sequencing — 4 Ways to Determine Next Address

1. **Incrementing the CAR** — sequential microinstructions (most common)
2. **Unconditional branch** — jump using the address field of current microinstruction
3. **Conditional branch** — depends on a status bit (e.g., branch only if Carry = 1)
4. **Mapping from instruction opcode** — used at start, to jump into correct microprogram for the fetched instruction

---

## 7. Mapping Process

```
Opcode:        1  0  1  1
                    │
        ┌───────────┴───────────┐
        │   0  (fixed prefix)     │  ← MSB set to 0
        └───────────┬───────────┘
                    │
         Mapped Address:  0 1 0 1 1 0 0
                          (opcode placed in specific bit positions,
                           rest padded with 0s)
```

**General rule**: take the opcode bits and place them into specific bit positions of the control memory address, padding the rest with 0s → gives a unique starting address for each instruction's microprogram, without complex decode logic.

## 8. Where Data Actually Lives — Datapath Registers

The control unit generates **commands**; the **datapath registers** hold the actual **data** those commands act on.

| Register | Full Name | What it holds |
|---|---|---|
| **PC** | Program Counter | Address of the *next* instruction to fetch |
| **AR** | Address Register | Holds a memory address currently being accessed |
| **DR** | Data Register | Holds data fetched from or to be written to memory |
| **AC** | Accumulator | Main register where arithmetic/logic operations are performed and results stored |
| **IR** | Instruction Register | Holds the instruction currently being executed (opcode + address part) |
| **TR** | Temporary Register | Holds intermediate data during multi-step operations |
| **INPR** | Input Register | Holds data from input device |
| **OUTR** | Output Register | Holds data going to output device |
| **E** | Extended Accumulator (Carry flip-flop) | Holds carry-out bit from AC during arithmetic |

**Where operations physically happen**: the **ALU**. Data flows from registers (AC, DR) into the ALU, gets operated on, and the result is written back into AC.

### Example — `ADD` Instruction Walkthrough

| Micro-step | Micro-operation | Where data is |
|---|---|---|
| 1 | `AR ← IR(address part)` | Address sits in **AR** |
| 2 | `DR ← M[AR]` | Operand fetched from memory into **DR** |
| 3 | `AC ← AC + DR, E ← Carry` | ALU adds AC and DR, result → **AC**, carry-out → **E** |

### Datapath Mental Model

```
        ┌─────────────────────────────┐
        │         Common Bus            │
        └───┬───┬───┬───┬───┬───┬─────┘
            │   │   │   │   │   │
           PC  AR  DR  AC  IR  TR   ← registers connected to bus
                        │
                       ALU  ← operations physically happen here
                        │
                    result → back onto bus → into destination register
```

Every micro-operation = **"take data from Register X, optionally push it through the ALU, and load the result into Register Y."**

## 9. The Fetch Cycle — Detailed

**The fetch cycle is itself a microprogram** — a fixed sequence of microinstructions in Control Memory, common to every machine instruction. Every instruction starts by running through this same fetch microprogram before branching to its own specific microprogram.

### Step-by-Step Fetch

| Step | Microinstruction | What happens |
|---|---|---|
| 1 | `AR ← PC` | Address of next instruction moves from PC to AR |
| 2 | `DR ← M[AR], PC ← PC + 1` | Word at memory[AR] fetched into DR; PC incremented in parallel |
| 3 | `IR ← DR` | Fetched word (the instruction) moved from DR into IR |
| 4 | `CAR ← Map(IR opcode)` | Opcode sent to mapper → CAR loaded with starting address of that instruction's microprogram |

### Full Sequence Visualized

```
┌─────────────────────────────────────────────┐
│              FETCH MICROPROGRAM               │
│         (same for every instruction)           │
├─────────────────────────────────────────────┤
│  1.  AR ← PC                                   │
│  2.  DR ← M[AR] ,  PC ← PC + 1                 │
│  3.  IR ← DR                                   │
│  4.  CAR ← Map(IR opcode)  ──► branches to       │
│                                the specific       │
│                                instruction's       │
│                                microprogram        │
└─────────────────────────────────────────────┘
                        │
                        ▼
        ┌───────────────────────────────┐
        │   Instruction-specific micro-    │
        │   program (e.g., ADD, MOV, etc.)  │
        │   executes using AC, DR, ALU      │
        └───────────────────────────────┘
                        │
                        ▼
        After last microinstruction of that
        instruction → CAR ← address of Fetch
        routine again → cycle repeats for
        next instruction
```

### Why This Design Is Elegant
- The **fetch routine is stored only once** in Control Memory — every instruction's microprogram jumps back to this same shared routine. No duplication.
- Different from hardwired control, where fetch logic is built into fixed circuitry, not reusable stored microcode.
- The **mapping step** is the bridge between "generic fetch" and "instruction-specific execution."

## 10. The Explicit Return-to-Fetch (Important Clarification)

**There is no implicit or automatic return to Fetch.** The control unit is a hardware state machine — it always needs an explicit address to go to next. Every microprogram, no matter how short, **must end with an explicit unconditional branch microinstruction** whose target is the Fetch routine's starting address.

### Example

```
ADD microprogram:
  μ-instr 1:  AR ← IR(addr)                    → next: sequential
  μ-instr 2:  DR ← M[AR]                        → next: sequential  
  μ-instr 3:  AC ← AC+DR, E←Cout, CAR ← FETCH   → next: JUMP to Fetch (explicit!)
```

This is exactly like a subroutine needing an explicit `RET`/`JMP` — nothing happens automatically. The microprogrammer (or microcode assembler) designs every instruction's microcode to terminate this way.

> Every microinstruction — including the last one of any microprogram — has its branch/address field filled in. It's never empty.

## 11. One-Cycle-Per-Microinstruction — Precision Notes

- Each microinstruction typically takes **one clock cycle** to be read from Control Memory and executed.
- Cycle flow: CAR addresses CM → microinstruction read out → control signals fire → micro-operation(s) performed → sequencer computes next CAR value.
- **Not every next-address is "jump to fetch"** — only the sequencing field of the *very last* microinstruction of an instruction's microprogram loads CAR with the Fetch routine's address. Mid-program, next address can be sequential, conditional, or an unconditional branch elsewhere.
- Fetch itself has **no special hardware status** — it's just another microprogram sitting in CM like ADD's or MOV's. The only special thing is that every instruction's microprogram ends by branching to it.

### Full Precise Definition (memorize)

> A microprogram is a sequence of microinstructions stored in Control Memory. Each microinstruction is fetched using the address in CAR, executed in one clock cycle (generating control signals for that step's micro-operations), and the sequencing field of that microinstruction determines the next CAR value — either sequential, conditional, or branch. When the microprogram for a machine instruction finishes, its final microinstruction loads CAR with the starting address of the Fetch microprogram, which itself is just another set of microinstructions stored in CM. This restarts the cycle for the next machine instruction.

## 12. Link to RISC vs CISC Pipelining (Common Follow-up Question)

**Misconception to avoid**: The "jump back to fetch" mechanism itself is NOT why CISC struggles with pipelining — this mechanism exists in every microprogrammed control unit, RISC or CISC.

**Real cause: variability**

| Cause | Why it breaks pipelining |
|---|---|
| **Variable number of microinstructions per instruction** | `MOV` might take 3 microinstructions, `MULT` (memory-to-memory) might take 20+ — breaks the uniform-timing assumption pipelines rely on |
| **Variable-length instruction encoding** | Fetch stage can't predict where the next instruction starts until decoding the current one finishes — stalls overlap |
| **Memory operands directly in ALU instructions** | Multiple mid-execution memory accesses cause unpredictable stalls that ripple through pipeline stages |
| **Complex addressing modes** | Different modes take different cycles to resolve effective address — breaks uniform stage timing |

**Correct framing**:
> It's not the jump-back-to-fetch instruction itself — it's that each machine instruction's microprogram has a different, unpredictable *length* before it reaches that jump. Since CISC instructions vary wildly in complexity, you can't predict when the next Fetch will begin. Pipelining requires the next instruction's fetch to overlap predictably with current execution — and if you don't know how many cycles until this instruction's microprogram finishes, you can't reliably overlap stages.

**Why RISC avoids this**:
- Every instruction is designed to take a fixed, small number of cycles (ideally 1)
- The "return to fetch" happens at a predictable, uniform point every time
- Pipeline stages take the same amount of time → safe to overlap Fetch/Decode/Execute of consecutive instructions

### Final Corrected Statement

> CISC's pipelining difficulty isn't caused by the jump-back-to-fetch mechanism itself (which exists in all microprogrammed control) — it's caused by the unpredictable and variable length of each instruction's microprogram before that jump happens, making the timing of "when the next fetch begins" inconsistent across instructions. RISC solves this by keeping every instruction's execution length fixed and short (ideally one cycle), making pipeline stage timing uniform and predictable.

## 13. Advantages & Disadvantages

| Advantages | Disadvantages |
|---|---|
| Systematic, organized design | Slower than hardwired control (extra memory access per micro-op) |
| Easy to design and debug | More expensive (needs control memory) |
| Easy to modify (especially with dynamic/writable CM) | — |
| Supports complex instruction sets efficiently (good fit for CISC) | — |
| Less hardware complexity vs. equivalent hardwired logic for complex instruction sets | — |

## 14. One-Line Definitions — Rapid Fire

- **Control word** = binary pattern specifying micro-operations to be performed
- **Microprogram** = sequence of control words (microinstructions) for one machine instruction
- **Microprogram sequencer** = generates next CM address based on current microinstruction + status conditions
- **Mapping** = process of converting an opcode into the starting CM address of its microprogram
- **Horizontal microinstruction** = one bit per control signal, faster, longer word
- **Vertical microinstruction** = encoded control signals, slower (needs decoder), shorter word

---

## 15. Master Mental Model (Say This Out Loud to Revise)

> **Fetch the machine instruction → map its opcode to a CM address → treat that address like a mini-program counter → execute microinstructions one by one, each one firing control signals (acting on registers like AC, DR, AR via the ALU and bus) and deciding the next address → when the microprogram ends (explicit branch, never automatic), jump back to the Fetch microprogram stored in the same Control Memory → repeat for the next machine instruction.**
